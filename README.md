# رَفِيق — إصدار المصدر 0.4.10

تطبيق Flutter عربي للمصحف والحفظ والتسميع. يستخدم نموذج Quran-Lab Zipformer v3.1 محليًا عبر Sherpa-ONNX. **ملف النموذج الكبير منفصل عن APK** حتى لا تضطر إلى تنزيل نحو 110 ميجابايت مع كل تحديث للتطبيق.

## كيف تبني APK على GitHub Actions

**قبل أول بناء:** اجعل مستودع GitHub خاصًا إذا أردت أن يرفق workflow حزمة النموذج الكبيرة كـ artifact، وجهّز أسرار توقيع الإصدار الثابتة الموضّحة في قسم «الحفاظ على النموذج عند تحديث APK» أسفل هذا الدليل. النموذج يتطلب موافقة وصول ورخصة NPL-1.2؛ لذلك لا تُرفع أوزانه كـ artifact في مستودع عام. إن بنيت أول نسخة بمفتاح debug ثم أضفت مفتاحًا آخر لاحقًا، فقد يتعذّر تثبيت النسخة الجديدة كتحديث فوقها. يلزم أيضًا سر `HF_TOKEN` للوصول إلى النموذج.

1. ارفع محتويات هذا المجلد إلى **جذر** مستودع GitHub (يجب أن يظهر `.github/workflows/android_build.yml` و`pubspec.yaml` و`lib/` مباشرة في الجذر).
2. اطلب صلاحية الوصول إلى نموذج `Quran-Lab/zipformer_p-arabic-v3` على Hugging Face واقبل رخصته، ثم أنشئ read token.
3. أضف الرمز إلى `Settings → Secrets and variables → Actions` باسم `HF_TOKEN`.
4. ادفع commit إلى `main` أو شغّل `Actions → Rafiq Android APK → Run workflow`.
5. نزّل `rafiq-v0.4.10-arm64-apk` لمعظم الهواتف الحديثة، أو `rafiq-v0.4.10-arm32-apk` لبعض الأجهزة الأقدم.

## التثبيت الأول للنموذج — مرة واحدة

في أول بناء بعد تغيير مفتاح cache سيظهر Artifact إضافي اسمه **`rafiq-model-v3.1-pack`** إذا كان مستودع GitHub خاصًا. في المستودع العام يمنع workflow رفع ملفات النموذج المقيد، لكنه يستطيع بناء APK خفيف. نزّله مرة واحدة إلى الهاتف، وافتحه/فك ضغطه في مجلد يمكن الوصول إليه عبر منتقي الملفات. ثبّت APK وافتح رَفِيق، ثم اختر الملفات الخمسة معًا من زر **«استيراد حزمة النموذج مرة واحدة»**:

- `model.int8.onnx`
- `tokens.txt`
- `quran_phoneme_words.json`
- `QURAN_LAB_NPL_1_2_LICENSE.txt`
- `model_manifest.json`

يتحقق التطبيق من metadata وبصمات SHA-256 قبل تفعيل النموذج. يُنسخ النموذج إلى مساحة التطبيق الخاصة ولا يُحمّل كاملًا في ذاكرة Dart. بعد الاستيراد، تعمل القراءة دون إنترنت. في تحديثات APK العادية يبقى النموذج مثبتًا؛ **لا تحذف التطبيق ولا تمسح بياناته** إذا أردت تجنب استيراده مجددًا. إذا انتهت صلاحية Artifact أو فقدته، شغّل workflow يدويًا مع اختيار `include_model_pack=true` لإعادة إرفاقه. قد تعيد GitHub تنزيل الملفات إذا انتهت cache أو تغيّرت نسخة النموذج، لكن هذا لا يحدث في كل تحديث للكود عادةً.


## الحفاظ على النموذج عند تحديث APK (توقيع ثابت)

حتى يسمح Android بتثبيت APK جديد كتحديث فوق السابق، يجب توقيع جميع الإصدارات بالمفتاح نفسه. أنشئ ملف keystore مرة واحدة على جهاز موثوق باستخدام JDK:

```bash
keytool -genkeypair -v -keystore rafiq-release.jks -alias rafiq -keyalg RSA -keysize 2048 -validity 10000
base64 -w 0 rafiq-release.jks  # Linux / Git Bash
```

على macOS يمكن استخدام `base64 rafiq-release.jks`، وفي Windows PowerShell: 

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("rafiq-release.jks"))
```

انسخ النص الناتج إلى GitHub Actions Secret اسمه `RELEASE_KEYSTORE_BASE64`، وأضف الأسرار `RELEASE_STORE_PASSWORD` و`RELEASE_KEY_ALIAS` (القيمة `rafiq` إذا استخدمت الأمر أعلاه) و`RELEASE_KEY_PASSWORD`. لا ترفع ملف keystore أو كلمات المرور إلى Git. احتفظ بنسخة احتياطية آمنة من المفتاح؛ فقدانه يمنع تحديث التطبيق الموقع به. إذا لم تضف الأسرار، سيظهر تحذير وقد لا يقبل Android APK من بناء لاحق كتحديث مباشر، وقد تضطر إلى إزالة التطبيق وإعادة استيراد النموذج.

## التحسينات الفعلية في المصدر

- التقاط PCM أحادي عند 16 kHz ومحرك Sherpa-ONNX في Isolate.
- تمرير الرموز والتوقيتات وزمن الاستدلال مع رقم الجلسة والتسلسل، ورفض النتائج القديمة.
- تفريغ آخر مقطع صوتي وانتظار معالجة المقاطع المرسلة قبل إغلاق جلسة الاستماع.
- مطابقة `tokens.txt` مقابل المرجع حين تكون الرموز قابلة للترميز بالكامل، وإعلان المسار الاحتياطي الأقل موثوقية.
- تحسينات للتلعثم والتصحيح الذاتي، ومنع تسجيل الخطأ المبدئي كخطأ دائم، وعدم اعتبار المرجع الفونيمي المفقود إجابة صحيحة.
- التحقق من SHA-256 للنموذج والرموز والمعجم والترخيص ومنع مزج إصدارات غير متوافقة.
- نواة مستقلة لمحاذاة CTC بـ Viterbi، ودرجة مقارنة محلية LLR، ومتعقب tempo، وشبكة بدائل الوصل والوقف، مع اختبارات خوارزمية اصطناعية ولوحة تشخيص للمطور.

## حد تقني مهم

واجهة `OnlineRecognizerResult` العامة في ربط Dart الخاص بـ Sherpa تعرض `text` و`tokens` و`timestamps`، ولا تعرض احتمالات CTC الخام لكل إطار. لذلك لم تُربط بعد نواة CTC Viterbi وGOP/LLR وقياس المد والغنة بمخرجات الاستدلال الحية. لا تعرض الواجهة درجات احتمالية أو أحكامًا زمنية مصطنعة؛ لا يزال التقييم الصوتي المتخصص للإخفاء والإدغام والغنة والقلقلة والتفخيم والترقيق بحاجة إلى مسار دليل صوتي مناسب ومعايرة على تسجيلات بشرية موسومة.

لا يستطيع أي ASR ضمان كشف كل خطأ في كل تسجيل. نجاح البناء يثبت سلامة مسار البناء والاختبارات المتاحة، لكنه لا يثبت دقة علمية لكل قاعدة تجويد.

## تحقق البناء

يُشغّل GitHub Actions اختبارات Python، و`dart format` و`flutter analyze` و`flutter test` ثم يبني APKs ويرفع checksums. لم يتوفر Flutter/Dart داخل بيئة إعداد الأرشيف، لذلك يجب اعتماد نتيجة GitHub Actions بوصفها فحص البناء الفعلي قبل تثبيت APK.
